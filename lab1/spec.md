# Мета

Призначення ER-моделі: планування робочих змін, призначення працівників на зміни та погодження обміну змінами

# Сутності та атрибути

| Сутність             | Атрибути               |
| -------------------- | ----------------------------------------------- |  
| EMPLOYEE | id, first_name, last_name, email, phone |
| STORE | id, name, address |
| ROLE | id, name |
| SHIFT | id, start_time, end_time, capacity  |
| SHIFT_ASSIGNMENT | id, assigned_at, status |
| SWAP_REQUEST | id, created_at, reason |
| UNAVAILABILITY | id, start_time, end_time |
| SWAP_APPROVAL | id, approver_type, decision, decided_at, rejection_reason|
| SWAP_STATUS_HISTORY | id, previous_status, new_status, changed_at, change_reason|

# Типи даних

| Атрибути             | Тип        |
| -------------------- | ---------- |
| id                 | int      |
| Імена, адреси, назви | string  |
| Телефон та email     | string   |
| Дата й час           | datetime |
| Причина заявки       | string   |
| status              | enum    |
| approver_type             | enum  |
| decision             | enum  |
| capacity              | int  |
| previous_status | enum, необов'язковий |
| new_status | enum |
| change_reason | string, необов'язковий |
| rejection_reason | string, обов'язковий лише при відхиленні |
| decided_at | datetime |

| Атрибут                               | Допустимі значення                                                         |
| ------------------------------------- | -------------------------------------------------------------------------- |
| `SHIFT_ASSIGNMENT.status`             | `active`, `cancelled`                                                      |
| `SWAP_APPROVAL.approver_type`         | `employee`, `manager`                                                      |
| `SWAP_APPROVAL.decision`              | `approved`, `rejected`                                                     |
| `SWAP_STATUS_HISTORY.previous_status` | `pending_employee`, `pending_manager`, `approved`, `rejected`, `cancelled` |
| `SWAP_STATUS_HISTORY.new_status`      | `pending_employee`, `pending_manager`, `approved`, `rejected`, `cancelled` |

Усі атрибути обов'язкові, якщо не зазначено інше.

# Бізнес-обмеження

| №     | Бізнес-правило                                                                                      |
| ----- | --------------------------------------------------------------------------------------------------- |
| BR-01 | Працівник може працювати в магазині, до якого його не прикріплено.                                  |
| BR-02 | Ролі працівників діють глобально.                                                                   |
| BR-03 | Початок зміни передує її завершенню. Нічні зміни заборонені.                                        |
| BR-04 | Місткість зміни є додатним цілим числом. Кількість чинних призначень не перевищує `capacity`.       |
| BR-05 | Працівник повинен мати необхідну для зміни роль.                                                    |
| BR-06 | Чинні зміни одного працівника не перетинаються та не є суміжними.                                   |
| BR-07 | Для однієї пари працівник–зміна допускається лише одне чинне призначення.                           |
| BR-08 | Працівник доступний за замовчуванням.                                                               |
| BR-09 | Призначення на період недоступності заборонене.                                                     |
| BR-10 | Заявка на обмін стосується двох різних призначень різних працівників.                               |
| BR-11 | Обмін змінами між магазинами дозволений.                                                            |
| BR-12 | Міжмагазинну заявку створює один із відповідних менеджерів.                                         |
| BR-13 | 	Для міжмагазинного обміну потрібна згода двох різних менеджерів відповідних магазинів та обох учасників обміну. |
| BR-14 | Призначення може брати участь у декількох відкритих заявках.                                        |
| BR-15 | Заявки, які після оновлення графіка суперечать бізнес-правилам, скасовуються.                       |
| BR-16 | Після погодження обміну попередні призначення отримують статус cancelled, а замість них створюються нові. Скасовані призначення, рішення учасників та історія статусів зберігаються. |
| BR-17 | Поточний статус заявки визначається за останнім записом історії за changed_at. При однаковому часі пізніший запис має більший id. |
| BR-18 | Ідентифікатори сутностей, email працівників та назви ролей унікальні.                               |
| BR-19 | Початок періоду недоступності передує його завершенню. |
| BR-20 | Для обміну в одному магазині потрібна згода одного менеджера та обох учасників. Якщо один з учасників є менеджером, потрібна згода двох інших уповноважених менеджерів. |
| BR-21 | Менеджер, який погоджує заявку від імені магазину, повинен мати роль менеджера та бути прикріпленим до відповідного магазину. |
| BR-22 | 	Кожна особа може прийняти лише одне рішення щодо заявки. Учасник обміну не може погоджувати заявку від імені магазину. За відсутності необхідних погоджень заявка не може бути затверджена. |
| BR-23 | При створенні заявки формується початковий запис історії зі статусом `pending_employee`. |
| BR-24 | Після згоди обох працівників заявка переходить у `pending_manager`. Після згоди всіх необхідних менеджерів — в `approved`, якщо обмін відповідає бізнес-правилам. Відмова будь-якого необхідного учасника переводить заявку в `rejected`. |
| BR-25 | Запис погодження менеджера обов'язково пов'язаний із відповідним магазином, а погодження працівника не потребує такого зв'язку. |
| BR-26 | Усі часові значення використовують єдиний локальний час. Часові пояси не моделюються. |

# Критерії прийняття

| Критерій | Новий зміст                                                            |
| -------- | ---------------------------------------------------------------------- |
| AC-01 | Рівно дев'ять визначених сутностей з усіма зазначеними атрибутами |
| AC-02 | Усі 15 зв'язків та їхні кардинальності відповідають таблиці зв'язків |
| AC-03    | Чисті M:N залишаються прямими зв'язками                                |
| AC-04    | SHIFT_ASSIGNMENT та SWAP_APPROVAL містять власні атрибути              |
| AC-05 | Атрибути атомарні, відсутні часткові та транзитивні залежності неключових атрибутів |
| AC-06 | Узгоджені назви та типи атрибутів, усі ідентифікатори мають тип int |
| AC-07    | Використано Mermaid erDiagram                                          |
| AC-08    | SVG згенеровано з декларативної моделі, діаграма читабельна            |
| AC-09    | Відсутня фізична схема БД                                              |
| AC-10 | Заявка пов'язана з двома призначеннями, автором заявки та окремими записами погодження |
| AC-11    | UNAVAILABILITY описує виключно недоступність                           |
| AC-12    | Ролі є глобальними                                                     |
| AC-13 | Зберігається історія переходів статусів заявки без дублювання поточного статусу в SWAP_REQUEST |
| AC-14    | Для зміни визначені необхідна роль та кількість місць                  |
| AC-15    | Модель підтримує збереження причин відхилення заявок                   |
| AC-16    | Модель підтримує визначені бізнес-правила, а обмеження, які неможливо виразити засобами Mermaid, задокументовані окремо                  |
