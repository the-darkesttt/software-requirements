# Фінальна перевірка ER-моделі ShiftManager

[Поточна модель](../model.mmd) відповідає [уточненій специфікації](../spec.md). Для BR-13, BR-20 і BR-22 достатньо наявних сутностей, атрибутів і зв’язків. Декларативну модель і SVG залишено без змін.

## Уточнені правила погодження

| Правило | Що підтримує модель |
|---|---|
| BR-13 | Для міжмагазинного обміну можна зберегти згоду обох учасників і ще два рішення від різних менеджерів, по одному для відповідного магазину. `SWAP_APPROVAL` пов’язує кожне рішення із заявкою, конкретним працівником і, для рішення менеджера, магазином. Магазини обміну визначаються через `offered` і `requested`, їхні зміни та магазини. |
| BR-20 | Для обміну в одному магазині можна зберегти рішення обох учасників і одного менеджера. Якщо один з учасників є менеджером, можна зберегти рішення обох учасників і двох інших уповноважених менеджерів для того самого магазину. Кардинальність `0..N` з боку записів рішення підтримує обидва сценарії. |
| BR-22 | Працівник, який ухвалив рішення, і заявка визначені для кожного `SWAP_APPROVAL`. Це дає змогу перевірити єдине рішення для пари особа–заявка незалежно від `approver_type`. Учасників обміну можна визначити через два призначення й виключити з погодження від імені магазину. Для переходу в `approved` потрібен повний набір згод за відповідним сценарієм. |

Відкриті питання з [попереднього звіту](004-er-revision-response.md) усунено. BR-20 визначає виняток для обміну в одному магазині за участю менеджера. BR-13 прямо вимагає двох різних менеджерів, навіть якщо одна особа прикріплена до обох магазинів. BR-22 забороняє кілька рішень однієї особи щодо заявки і погодження від імені магазину учасником обміну.

## Критерії прийняття

| Критерій | Результат |
|---|---|
| AC-01 | Виконано. Рівно дев’ять сутностей із визначеними атрибутами. |
| AC-02 | Виконано. Звірено всі 15 зв’язків і кардинальності на обох кінцях. |
| AC-03 | Виконано. `EMPLOYEE–STORE` та `EMPLOYEE–ROLE` є прямими M:N. |
| AC-04 | Виконано. `SHIFT_ASSIGNMENT` і `SWAP_APPROVAL` мають власні атрибути. |
| AC-05 | Виконано за залежностями специфікації. Атрибути атомарні. Уточнене обмеження на пару особа–заявка стосується запису рішення в цілому. Часткових чи транзитивних залежностей неключових атрибутів не виявлено. |
| AC-06 | Виконано. Назви й типи відповідають специфікації, усі ідентифікатори мають тип `int`. |
| AC-07 | Виконано. Використано Mermaid `erDiagram`. |
| AC-08 | Виконано. SVG відповідає декларативній моделі. Перевірено структуру та розташування підписів. |
| AC-09 | Виконано. Артефакти описують концептуальну модель без фізичної схеми БД. |
| AC-10 | Виконано. Є окремі зв’язки `offered` і `requested`, автор заявки та записи погоджень. |
| AC-11 | Виконано. `UNAVAILABILITY` описує лише недоступність. |
| AC-12 | Виконано. Ролі працівника глобальні. |
| AC-13 | Виконано. Історія статусів зберігається окремо. Поточний статус заявки визначається з історії. |
| AC-14 | Виконано. Зміна має одну необхідну роль і `capacity`. |
| AC-15 | Виконано. Причина відхилення зберігається в `SWAP_APPROVAL.rejection_reason`. |
| AC-16 | Виконано на рівні концептуальної моделі. Даних достатньо для правил погодження. Обмеження Mermaid задокументовано нижче та в попередньому звіті. |

## Перевірка SVG

Прочитано [SVG](../model.svg) як XML і звірено з `model.mmd`. Збігаються всі дев’ять блоків сутностей, атрибути з типами й позначками, усі 15 пар кінців зв’язків, їхні підписи та маркери кардинальності. Підписи мають окремі позиції, а `offered` і `requested` — окремі лінії. Обидва артефакти відповідають версіям із коміту `05e9514`. Команду попередньої генерації зафіксовано у звіті 004. Повторний рендеринг не знадобився.

## Обмеження Mermaid

- Кардинальності дозволяють зберегти рішення. Вони не перевіряють унікальність пари особа–заявка, відмінність осіб менеджерів, відповідність менеджера магазину, виключення учасників з погодження від імені магазину або наявність повного набору згод перед переходом в `approved`.
- Потрібні окремі бізнес-перевірки для умовної обов’язковості магазину й причини відхилення, порядку переходів статусу та визначення поточного статусу за `changed_at` і `id`.
- Задокументовані у звіті 004 обмеження щодо часових інтервалів, ролей, недоступності, місткості та чинних призначень залишаються актуальними. Формулювання про одне рішення на роль із того звіту замінює уточнене BR-22, за яким дозволено одне рішення на особу щодо заявки.
